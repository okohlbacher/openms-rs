# mzML semantic validation

The optional `mzml-validation` feature implements the complete class-specific `MzMLValidator` operation group and `MzMLFile::isSemanticallyValid` convenience against SDK `82ce5b373c97f934ffd9b1ffd80215ca66473d0b`. It depends on the existing `mzml` and `semantic-validation` features, is outside defaults, and adds no dependency. This is CV mapping/value/unit validation, not XML Schema validation, binary decoding, footer/checksum validation or a complete `MzMLFile` claim.

## Public API

`format::mzml_validator::MzMLValidator::new(&CVMappings, &ControlledVocabulary)` borrows immutable providers. `validate(path)` and `validate_reader(BufRead)` return an owned `ValidationReport`; `locate_term(path, &ParsedCVTerm)` performs mapping selection only. `ValidationReport::is_valid()` means there are no semantic errors; warnings do not make that predicate false. XML, I/O, provider, numeric counter and resource failures return `Err` without a partial report. Reusing an instance cannot retain document state.

The public `options: ValidationOptions` covers every inherited source setter: CV tag; accession/name/value/unit-accession/unit-name attributes; value checking; unit checking; and native limits. All names are literal qualified XML names. Unit checking defaults **on** for MzMLValidator, whereas the general SemanticValidator defaults it off. Value checking defaults on. No source copy constructor exists; normal owned reports and borrowed providers avoid hidden file/parser ownership.

`mzml::validate_semantics(path)` uses the exact pinned `ms-mapping.xml` and existing five-provider `ControlledVocabulary::psi_ms()` singleton. `validate_semantics_with_options(path, &options)` accepts explicit checks/limits without cloning user configuration. The fixed mapping is included in the library and initialized once with the existing CVMappingFile parser/limits; CV initialization has its own existing fixed allowance. No environment-dependent OpenMS data directory, ontology download, schemaLocation fetch or runtime XML stylesheet is used. Paths use the existing content-sniffed plain/gzip/bzip2 transport.

## Complete source specialization

The same bounded `cv_xml` parser and semantic rule engine serve both validators. The only base extraction separates encounter-time unknown/obsolete diagnostics from known-term rule/value/unit handling, and shares the existing mapping-only locate operation. General validator behavior and its original fixture suite remain unchanged.

- A leading literal `indexedmzML` is removed from diagnostic/mapping paths. Same-named children and prefixed spellings remain literal. Empty parent paths retain the source `//cvParam/@accession` edge case.
- Known CV terms in `referenceableParamGroup` are stored in order and applied at every `referenceableParamGroupRef` location. Unknown terms warn at definition/inline encounter and are not stored. Obsolete terms warn at encounter, not again for every reference. Name/value/unit/rule checks wait until an actual application.
- Duplicate group definitions append. Unknown/forward references initially contribute no terms; later definitions do not retroactively apply them. Empty IDs remain ordinary keys. The native scientific mzML reader has stricter reference-integrity rules; this semantic validator intentionally preserves the different source validator behavior.
- A nested definition changes the source's current group ID; closing it does not restore the previous ID. User parameters are not CV group terms. Fixed group/ref/binary-array tag branches take precedence over the configurable CV tag even if the configured spelling collides.
- GO and BTO terms skip mapping/value/unit checks after encounter-time existence/obsolete handling. They do not satisfy mapping cardinality. `locate_term` remains the inherited mapping predicate and does not apply this exclusion.
- Every binaryDataArray start resets its remembered role/type. Strict descendants of `MS:1000513` select the role; strict descendants of `MS:1000518` select the type. Once both are present, the role's `xref_binary` list is checked on every subsequent handled term, so repeated mismatch errors retain source order. Inline and referenced terms share this state. The source suffix test is literally `/binaryDataArray/cvParam/@accession`; changing those configurable names disables that particular binary-role check, as in C++.
- Known terms then use the complete shared rule engine: first matching term in each rule, source collision/repeat/cardinality behavior, value and name messages, unit checks and diagnostic order. Scope and term-name mapping fields remain source-compatible, as do the documented SHOULD omission and permissive scalar conventions.

No CV syntax is inferred from native spectrum objects, and no unsupported scientific payload needs decoding to validate its CVs. The parser still checks the entire XML document and its text, declarations, attributes and nesting under the existing shared lexical/encoding policy. It does not enforce the mzML XSD's element order, required references or declared list counts.

## State, corrections and limits

Every document owns its group map, current ID, binary pair, rule counts, paths and diagnostics. [C++ issue CPP-051](../OpenMS_CPP_ISSUES.md) records source group definitions surviving even a **successful** earlier validation. A reused source instance can therefore accept a later document's undefined reference because the earlier group is still present. The native local state deliberately corrects that behavior; missing references within the current document retain the source empty-group semantics.

The reused engine preserves its established corrections [CPP-039, CPP-040 and CPP-044](../OpenMS_CPP_ISSUES.md): supplied-unit descendant comparison, no failed-document rule/stack contamination, and a stable checked error for an absent `locate_term` path. The source XSD_DATE handling still uses DateTime timestamp parsing, as documented in [CPP-046](../OpenMS_CPP_ISSUES.md); this group does not claim full XSD lexical conformance. The approved CV provider's typed-unit, XML, graph and historical-resource policies remain unchanged.

One per-document `ValidationLimits` allowance covers XML input/decoding, mapping indexes, group string/vector/tree ownership, each repeated reference inspection, descendant searches, rule counts, paths and diagnostics. A referenced term is borrowed from the stored group rather than deep-cloned; its actual repeated work and ensuing owned outputs are charged in the same meter. `max_terms` counts both encountered CV parameters and each expanded stored term. Empty/unknown references still consume XML/event/map resources. Sparse tree nodes and vector capacity growth are precharged before allocation; comparison work uses bounded keys. Reaching a limit never converts an error into an unknown-term warning or a semantic success.

Default limits remain those of general semantic validation: 16 MiB input, depth 128, one million XML elements/processed terms, 100,000 rules and diagnostics, one million mapping terms, 50 million work units and 128 MiB logical allocation allowance. These are configurable native limits, not source file-format limits. Cached immutable mapping/CV construction retains its separate fixed construction budgets. All custom test providers are borrowed, with no registry clone per document or reference.

## Evidence and validation

The direct `MzMLValidator_test.cpp` covers only construction/destruction; functional literals come from `MzMLFile_test.cpp:1203–1256`. Three unchanged upstream documents are retained under `tests/data/mzml_validator/`. The original source test assertions are extracted verbatim into `tests/data/mzml_validator_source.json` by `tools/generate_mzml_validator_reference.py`; this tool reads only the pinned C++ source. It preserves all 15 assertions over five source scenarios. Two scenarios depend on unavailable source-generated writer output: their zero/zero and zero/two warning expectations remain recorded as source assertions, not reassigned to native output.

The actual original valid and indexed fixtures produce zero errors/warnings; the original invalid fixture produces eight errors and one warning, matching the upstream class assertions. Dedicated independent tests pin exact diagnostic messages and ordering, complete configuration fields, group behavior, tag collisions, literal prefixes, nested IDs, binary pair order/reset/repeated diagnostics, GO/BTO handling, source-unit descendant correction, reuse after success/failure and cumulative term/work/diagnostic exhaustion after valid processing. A separate native empty-writer round trip checks semantic validity without claiming the source writer's warning count.

Rust 1.98/all-features and minimum Rust 1.85 with only `mzml-validation` enabled each pass all 16 direct tests, 28 general semantic/CVMapping public regressions and four private semantic resource tests. Strict scoped Clippy passes on both toolchains. An independent byte-hash regression protects the three original XML fixtures and embedded mapping from checkout normalization. No new C++ execution, XSD engine or upstream patch is claimed. Source, original fixture, reusable provider/mapping, projection and generator hashes are recorded in `tests/data/mzml_validator_provenance.json`.
