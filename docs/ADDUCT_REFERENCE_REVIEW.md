# Independent AdductInfo references

The [reference tests](../tests/adduct_reference.rs) exercise all native AdductInfo operations using the pinned source's scalar examples and separate calculations from its atomic and particle constants. The [manifest](../tests/data/adduct_provenance.json) records ten source hashes and the original decimal constant spellings. There are no C++ execution results or expected values generated by the native implementation.

## Scientific evidence

[AdductInfo_test.cpp](https://github.com/okohlbacher/OpenMS4-core/blob/7c029e8cdba6abab503708ecdd56f6ab55e38ce4/src/tests/class_tests/openms/source/AdductInfo_test.cpp) sets absolute tolerance `1e-3`. Its protonated monomer/dimer, deprotonated monomer, sodium shift, mass round trips, compatibility, and field checks are retained at that tolerance. These rounded examples alone would not distinguish electron compensation from several incorrect approximations.

Independent tighter checks use [Constants.h](https://github.com/okohlbacher/OpenMS4-core/blob/7c029e8cdba6abab503708ecdd56f6ab55e38ce4/src/openms/include/OpenMS/CONCEPT/Constants.h) and [ElementDB.cpp](https://github.com/okohlbacher/OpenMS4-core/blob/7c029e8cdba6abab503708ecdd56f6ab55e38ce4/src/openms/source/CHEMISTRY/ElementDB.cpp), without obtaining expected masses from the native formula APIs. For adduct atomic mass A, signed charge q and multiplier n, the source evaluates:

```
m/z = ((M*n + A) - q*electron_mass) / abs(q)
M = ((observed_mz*abs(q) - A) + q*electron_mass) / n
shift = A - q*(proton_mass + electron_mass)
```

The order of each expression is preserved. Average-mass shift substitutes only the average adduct atomic mass; its proton/electron compensation remains unchanged. Atomic hydrogen and the separately tabulated proton-plus-electron sum differ slightly, so the proton-adduct shift is small and nonzero. Sodium has one isotope of abundance one and equal average/monoisotopic masses; the upstream comment suggesting different sodium masses is not supported by the table or asserted as a numerical golden. Isotope-labeled carbon and deuterium provide an independent labeled-composition check.

## Parser and formula behavior

[AdductInfo.cpp](https://github.com/okohlbacher/OpenMS4-core/blob/7c029e8cdba6abab503708ecdd56f6ab55e38ce4/src/openms/source/CHEMISTRY/AdductInfo.cpp) removes spaces, tabs, newlines and carriage returns, retains the resulting name, and compares all four public identity fields. Leading zeros therefore remain significant to object equality even when the physical formula, charge and multiplier agree.

The reference suite retains several defined parser behaviors beyond the header's simplified grammar:

- A numeric-only term such as `M+2;1+` contributes an empty formula after its coefficient is stripped. `M+H-1;1+` retains H; the `-1` is a separate empty-formula term, not an H atom count of minus one.
- A zero stoichiometric coefficient is accepted. Zero charge and zero molecular multiplier are rejected.
- The final charge sign determines polarity after signed integer conversion. `M;-2+` has charge +2 and `M;+2-` has charge -2. The shared source integer helper strips one leading plus before parsing, so `M;+-2+` is also accepted. A repeated plus remains invalid.
- Negative element counts can be supplied through the typed formula constructor or arise by subtracting a fragment. The text parser splits every plus/minus in the formula part into operations; it does not delegate that complete expression to EmpiricalFormula.
- Existing formula isotope notation and D alias apply to fragments. The stored formula is neutral; supplying a charged formula to the constructor fails.

Malformed separators/operators, unknown elements, unsupported control whitespace, and out-of-range source integer tokens are checked separately from valid no-op terms.

## Compatibility and numerical boundaries

The source compatibility implementation is `candidate.contains(-adduct_formula)`. It ignores candidate charge and the n-mer multiplier. Thus a dimer losing two H still requires two H in the supplied candidate formula, rather than multiplying its atom counts by two. Natural and labeled isotopes remain distinct. Plus-only adducts are trivially compatible only when candidate atom counts are nonnegative; signed candidate formulas can fail the comparison.

The native formula stores i32 counts, whereas the pinned C++ map stores SignedSize counts. Arithmetic exceeding the native count range returns a checked error. Negating an adduct loss of i32::MIN would require 2,147,483,648 candidate atoms, which no native formula can represent; compatibility can safely return false for that case. A bare adduct remains compatible with any signed candidate because there are no required entries to compare.

The source implementation performs no positivity check on scalar masses despite a header note requiring positive observed m/z. Finite zero and negative inputs therefore retain their defined arithmetic. Nonfinite inputs, intermediate overflow, zero constructor invariants and i32::MIN charge produce checked native errors; the last replaces the source's undefined signed absolute value. The typed constructor can represent the full nonzero u32 multiplier range, while parsed multipliers follow the source's signed-i32 token conversion.

## Review and validation

All five independent references, eight direct API tests and enabled workflows pass in the final Cargo runs on Rust 1.96 and 1.85 with all features and without default features, and in the current-compiler idXML-only run. Strict all-target Clippy, rustdoc and formatting pass. Source hashes and original constant spellings are verified. The completed production review found no remaining actionable defect; no C++ code was built or executed.
