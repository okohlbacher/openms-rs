# mzML experimental headers and references

The mzML stream/path readers and both ordinary/Numpress writers transport the source-supported experimental header fields from SDK `82ce5b373c97f934ffd9b1ffd80215ca66473d0b`. They use the existing `MSExperiment.settings` owner and the full five-provider `ControlledVocabulary`; no second metadata map or reduced vocabulary is introduced. This completes the header/reference operation group. It does not complete `MzMLFile` or every mzML schema element. [Format-specific semantic validation](MZML_VALIDATOR_SUPPORT.md) is available separately. [Streaming consumers and transforms](MZML_CONSUMER_SUPPORT.md) and [centroid inspection](MZML_CENTROID_SUPPORT.md) are implemented as separate operation groups.

## Public operations and fields

Existing `mzml::read`, `read_with_options`, scientific loading and compressed path loading share one header registry. `read_metadata` and `read_metadata_with_options` return `ExperimentalSettings` without materializing records. `LoadOptions.scientific.metadata_only` returns an experiment containing those settings and empty spectrum/chromatogram vectors. The reader resolves the first list's required default processing reference and stops at its opening tag, before interpreting its count or reading binary/tail content. A document with no record list finishes normally. Unused scientific selection limits are not charged. [Disabled record population](MZML_CONSUMER_SUPPORT.md) now supports `fill_data=false`; other unimplemented scientific options remain explicit errors.

| XML owner | Native payload |
|---|---|
| mzML/run | Document accession, `mzml_id`, full run DateTime and retained raw timestamp, fraction identifier, typed run metadata |
| fileDescription | Ordered contacts; source-file names, paths, checksum/type, file/native-ID format and scalar metadata |
| sampleList/run sampleRef | Referenced sample name/number/mass/volume/concentration/state/comment, ordinary metadata and source PATO/BTO/GO routes |
| softwareList | Software name/version and typed scalar metadata; shared lookup is resolved before owned software copies |
| instrumentConfigurationList | Default instrument plus additional keyed configurations, software, customizations, instrument model and ion optics; complete source component enum/scalar/metadata routes |
| dataProcessingList | Encounter-ordered processing methods, software, actions, thresholds, completion DateTime and scalar metadata |
| records and auxiliary arrays | Default/explicit processing references; auxiliary float/integer/string array names, scalar metadata and processing histories |
| scans and precursors | Source-file name/path metadata, external spectrum IDs; scans can reference defined additional instruments |

The 116 instrument enum/accession pairs are independently projected from both C++ reader and writer branches and checked against source header discriminants. Remaining enum variants or stored fields that the source mzML writer cannot represent are rejected. Partial nonempty instruments must contain source, analyzer and detector families, as required by the XSD; an entirely empty instrument omits its optional component list. Component order retains the signed source scalar domain (`xs:int`). Unknown model/file/native-ID names, conflicting accession overrides and overrides with units are checked errors. Custom software names use the custom-software term rather than a lossy spelling alias.

Source files are deduplicated by complete value in lexical input-ID order. Record-only source files written into the document become global settings source files on reading, matching source list collection. Source-file size and arbitrary CV-term payload have no source writer representation and are rejected. A chromatogram cannot carry `sourceFileRef` in mzML: nondefault attached chromatogram SourceFile values and such input attributes are rejected. Spectrum source-file references and scan/precursor name/path references are supported. Additional instrument IDs retain caller identity; whitespace-normalized or generated-ID collisions fail before output.

Every processing reference clones only Arc handles after its definition has been parsed and validated. References to one definition share Arc identity, which is what makes that identity meaningful to a writer: the streaming `MSDataWritingConsumer` decides "differs from the first record's" with `Arc::ptr_eq` because the reader shares one `Arc` per `dataProcessingRef` exactly as source `processing_[ref]` shares one `shared_ptr`. Equal histories can be deduplicated during writing; no pointer identity is serialized. Methods retain XML encounter order on reading, as the source does, while writing emits their actual indices rather than repeating order zero. All list counts match the emitted definitions, including every array kind.

## Metadata and numerical fidelity

Headers, precursors and auxiliary arrays preserve strings, signed native integers, finite doubles and represented MS/UO units through the scalar codec. Empty/list values have no reversible scalar XML representation and fail before output. Source CV integer conversion narrows to i32 before native storage; user integers retain i64. Instrument/sample parsing follows source ListParse whitespace and leading-plus rules. BTO/GO lookup uses the full provider and preserves only fields actually consumed from its historical encoding.

CV promotion uses the independently projected source mapping-path membership rules, but only when the exact reader route returns the same metadata key/type. Otherwise a user parameter preserves the value. This fixes software metadata's wrong source mapping path and avoids moving ordinary metadata into a different dedicated field. All CV parameters precede user parameters. This is not MUST/cardinality/type/unit semantic validation or a replacement for the general mapping/validator APIs. Unknown terms ignored by source branches remain ignored; unresolved references and malformed recognized owners are checked errors by default. `ReadOptions::source_dangling_references` reads a dangling software, data-processing or source-file reference as the source does; see [Dangling references](#dangling-references-source-compatible-reading).

Legacy spectrum/chromatogram metadata is still string-valued. String, unit-free primary-array metadata is merged into that map: m/z before intensity for spectra regardless of XML order; XML encounter order for chromatograms. Incoming primary keys overwrite earlier keys exactly as source metadata addition does. Non-string/unit-bearing primary metadata and independent primary-array processing history are explicitly rejected because the current record has no owner for them. Auxiliary descriptions remain attached to their actual arrays through raw-f64 filtering, narrowing and aligned permutations.

`DataProcessing.completion_time` is now `Option<data_structures::DateTime>`, replacing `Option<CompletionTime>`. This is an API migration for explicit field construction; `.parse()` literals normally infer the new type. `None` denotes the source unset timestamp. Graph `ProcessingStep` retains its separate `CompletionTime` API. mzML, FeatureXML and ConsensusXML now preserve seconds and represented milliseconds. Writers reject invalid dates, inconsistent partial states and years outside 1–9999 before external output. Existing DateTime format/getter APIs perform the conversion; no timestamp shadow metadata is introduced. A stored raw run timestamp is reused only if its full parsed DateTime equals the current field, including milliseconds. Sample signed zero is preserved.

## Empty history and empty action sets

The schema requires a processing definition even for a native empty history. The writer emits one ConversionMzML method with exact fallback software name `OpenMS Rust mandatory mzML processing placeholder`, version `1`, and scalar marker `openms-rust:empty-processing-history="1"`. Only that exact payload normalizes back to empty. Real source conversion methods without the marker survive. That placeholder is written as its own `software id="so_default_empty_history"` entry, and only when some history is empty, so that `so_default` itself can be the source's empty `Software()`; see [C++ writer parity](MZML_WRITER_CPP_PARITY.md), which also lists the header's other source-writer alignments (root attributes, `cvList`, software identifiers and order, `run` identity and default source file, `processingMethod@order`, inherited `dataProcessingRef`, and the number text of inherited parameters).

An individual method with an empty action set emits a generic DataProcessing term plus `openms-rust:empty-processing-actions="1"`; its real software, timestamp and metadata remain. Only the action and marker are removed on reading. Both marker keys are reserved on native output. Reader eligibility checks raw element/attribute kinds, parameter/ref child shape, action multiplicity, discarded action values/units and ignored completion-time units, followed by complete semantic payload checks. Extra software payload or a forged marker cannot be silently discarded.

## Dangling references: source-compatible reading

Work package P2-MZML-LENIENCY, decision D10: tool paths get explicit source-compatibility load options, and library defaults stay strict. `MzMLHandler` looks software and data-processing references up with `std::map::operator[]`. A key that names no definition default-constructs the value, so the reference silently becomes an empty `Software` or an empty processing history. The upstream TOPP fixture `PeakPickerHiRes_5_input.mzML` (test-data `0cb15f2`, `TOPP_PeakPickerHiRes_5`, `CMakeLists.txt:2543-2545`) depends on this. Its `instrumentConfiguration ic_0` carries `<softwareRef ref="so_in_0"/>` with no `softwareList`, and its `chromatogramList` names `defaultDataProcessingRef="dp_sp_0"` with no `dataProcessingList`. The strict reader rejects it with `unresolved softwareRef`, and once that reference is removed, with `unresolved dataProcessingRef`.

### Preserved source conventions

- A dangling software reference yields a software with empty name, version and CV terms. A dangling processing reference yields an empty history, the same value as an absent attribute. Nothing else in the document changes: `PeakPickerHiRes_5_input.mzML` read with the option equals, as an `MSExperiment`, the strict read of a copy with the two references deleted.
- Resolved references in the same document keep sharing the definition's `Arc` handles, and a resolved method beside a dangling one keeps its software and encounter order.
- A software reference is resolved against the software defined before it, as the source copies `software_[ref]` at that point. An instrument list placed before the software list therefore gets empty software under the option, while a later `processingMethod` sees the definition. The executed oracle shows the same result.

### Native differences

- **Strict by default.** Without the option each case above is an error, because the reference cannot be kept. The source has no strict mode.
- **Warning.** Under the option, the first occurrence of each distinct dangling ID per kind in one read writes one line to the crate's warning log stream (`concept::log_stream`, `LogLevel::Warn`, standard error unless reconfigured), for example `Warning: mzML softwareRef 'so_in_0' names no definition; source-compatible reading uses empty software.` The source writes nothing here; the oracle's stderr holds no reference diagnostic. A tool run on such input therefore prints a warning where C++ is silent. A failure to write the warning never changes the read result.
- **Malformed IDs** stay errors under the option (`invalid parameter group ID/IDREF`). The source would look any string up.
- **Placeholder marker lookup.** The reader's check of the native empty-history marker indexed the software map with the raw `softwareRef` attribute. A whitespace-padded reference to the placeholder software, which ID normalization resolves, made that index panic on untrusted input. The lookup now uses the normalized ID, so the padded document reads under both settings. A dangling reference cannot name the placeholder, and a marker on it is refused (`processing marker contains additional or discarded XML payload`).

### Wave 8, decision D14: `sourceFileRef` joins the switch

D14 continues the lead-decision series of [VALIDATION](VALIDATION.md) (D1-D13), not the work-package series of [EARLY_TOPP_WORK_PACKAGES](EARLY_TOPP_WORK_PACKAGES.md), whose D10 opened this switch in the first place.

Wave 7 gave the streaming `MSDataWritingConsumer` a `ReferencePolicy::SourceDangling` that reproduces the `sourceFileRef="sf_sp_<s>"` source `MzMLHandler::writeSpectrum_` writes for every record after the first that carries a source file (`MzMLHandler.cpp:5252-5255`). Those identifiers name nothing the streamed header declares. With `sourceFileRef` outside this switch, the crate wrote, on any input with per-record source files, a file neither its own reader nor any strict reader would take back — while the C++ reader read both its own output and the port's. That is a self-inconsistency this project introduced, and D14 closes it by moving the reference kind into the switch: the reader accepts what the Release build accepts, and the refusal stays as the default strict profile. It reverses the "out of scope, stays strict" line drawn for `sourceFileRef` in P2-MZML-LENIENCY, deliberately.

What the Release build does with each shape was measured rather than only read, on `ibminode06` against the install at the pins (`../oracle/reader-roundtrip/probe_source_refs.cpp`, `logs/probe_06.log`):

| shape | C++ result | warning |
|---|---|---|
| spectrum `sourceFileRef` | the record's `SourceFile` stays default-constructed; nothing is inserted into `source_files_` | `Error: unregistered source file reference <id>.` once **per occurrence** |
| chromatogram `sourceFileRef` | `source_files_[ref]` default-constructs, inserts and sets an empty `SourceFile` | none |
| scan and precursor `sourceFileRef` | `source_file_name` and `source_file_path` are **present** with empty values | none |

The `operator[]` insertions a chromatogram, a scan or a precursor performs make the ID "known" for any later spectrum, which then takes the `contains` branch, sets the same empty value and does not warn. That side effect changes no data — the value set is the default either way — and the end-of-`sourceFileList` copy into `exp_->getSourceFiles()` (`:1499-1509`) runs before the run element, so the inserted entries never reach the experiment's source-file list. The measured `exp_source_files` count confirms it: one, the single declared entry, on a fixture naming two dangling IDs.

The port's warning stays native in frequency as well as wording: once per distinct ID per read, for every shape, where the source warns per occurrence and only for a spectrum's. `tests/mzml_source_file_round_trip.rs` holds the 52-line executed comparison, the strict refusals of all three shapes, the warning record, and the round trip itself — the crate writing a low-memory file from an input with per-record source files and reading it back.

## Bounds and failure behavior

Header capture, registry construction, reference expansion, metadata copying, deduplication and planned XML output use one cumulative 50,000,000-work/256 MiB allocation allowance per operation, separate from the existing XML/parameter/binary/selection limits and the immutable CV singleton's own initialization allowance. Every pre-run descriptor participates in `ReadOptions.max_total_params/max_param_bytes`; referenced parameter payload is charged again for each use. Retained header nesting is limited to 16. Full inline map value types are precharged before insertion, including sparse root capacity; vector minimum/geometric capacities and deep owned copies are covered. Shared processing attachments charge handles, not repeated deep copies. The shared data-array meter now conservatively charges at least 11 complete element slots for a nonempty BTree root, including large inline values; this can reject previously undercharged small custom allocation limits earlier.

Read operations build owned results, and path replacement stays transactional. Writer semantic/size failures occur before any external write. After output begins, external I/O failure can leave a partial stream, as for ordinary Rust writers; atomic path publication remains handled by the existing path layer. Neither format provides a promise to validate the unread metadata-only tail. Plain/gzip/bzip2 paths use the existing bounded, content-sniffed reader and atomic store transport.
