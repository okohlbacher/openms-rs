# Independent RNA foundation reference review

The reference suite covers the pinned OpenMS4-core `Ribonucleotide`, provider and
registry classes, and `NASequence`, at revision
`7c029e8cdba6abab503708ecdd56f6ab55e38ce4`. It does not claim to cover RNase
processing, `IdentificationData` RNA records, modified-RNA generation, or the
nucleic-acid spectrum generator. No C++ library was built or executed.

The provenance manifest is [rna_provenance.json](../tests/data/rna_provenance.json).
The package tests use embedded resources and small fixtures; they never read the
source checkout at runtime. The default dataset's notices and publication
boundary are maintained separately in [LICENSES.md](../LICENSES.md); scientific
reference coverage is not a claim about new permissions to redistribute data.

## Evidence and fixture construction

[The source class test](https://github.com/okohlbacher/OpenMS4-core/blob/7c029e8cdba6abab503708ecdd56f6ab55e38ce4/src/tests/class_tests/openms/source/NASequence_test.cpp)
provides the following complete numerical sections:

- [15 formula assertions](../tests/data/rna_source_formulas.tsv), including all
  original formula summands, fragment types, signed charges and line numbers.
- [23 mass assertions](../tests/data/rna_source_masses.tsv): 18 monoisotopic and
  five average cases. The table retains the original decimal expression,
  explicit divisor, evaluated expected value, and binary64 bits. Values such as
  `1848.587 + 0.734` remain recognizable as source expressions.
- [Ten positive slice examples](../tests/data/rna_source_slices.tsv), with
  source sequence, operation, arguments and expected text. Source failure cases
  and additional boundary conditions are asserted directly in the test.

These tables were extracted independently from the source text by a small
standard-library Python pass tracking sequence-variable assignments and literal
assertions. They were not generated by evaluating native sequence operations.
Formula summands are added by the test using the existing independently tested
empirical-formula type; no native RNA implementation computes the expected
fragment formula.

The source mass comments attribute references to Mongo-Oligo, other external
calculators, and the RNAModMapper publication. These rounded numbers are not
high-precision observations from an executed C++ implementation. In particular,
GGG's charge -2 a-B expectation `802.117` is approximate, and `1201.3` has one
decimal place. The reference test explicitly uses a relative tolerance of
`1e-5`, except absolute `0.05` for that one-decimal average reference. This is a
native acceptance policy for those published literals, not a claim about the
exact settings of the source's unavailable `ClassTest` macro. Exact elemental
assertions provide the stronger compositional checks.

The independent [378-row registry projection](../tests/data/rna_registry_reference.tsv)
was produced from the original JSON and custom TSV by separately transcribing
source provider rules. It was created before reading the root implementation's
generated registry expression. It records provider and original key/line, code,
formula, origin, terminal specificity, base-loss formula, alternatives, and
independent declared-mass bits. Formula-derived masses are tagged `formula`
rather than mislabeled as source decimal literals. The test computes these
fallbacks with the existing empirical-formula implementation.

All 378 iteration records and all 375 distinct codes are checked, including the
three duplicated JSON codes. `pm1acp3Y` and `pm2,7Gm` have differing formulas in
their duplicate records, so the test also pins their last-record lookup winners.
The current default load order is lexical JSON object-key order followed by the
45 custom TSV rows; the first code `io6A` is also an explicit source class-test
assertion. The `rna-json` feature additionally checks every parsed JSON record
against the embedded projection. TSV-versus-embedded comparison runs with or
without that feature. Original resource hashes are recorded independently of
the generated expression.

## Additional source-derived checks

[The reference tests](../tests/rna_reference.rs) also exercise the following
behaviors by direct inspection of the pinned algorithms:

- The source's purported all-record `toString` loop never reaches its assertion:
  it first continues for a code unequal to `c`, then continues for a code unequal
  to `p`. The new loop actually parses and checks reconstruction for every
  registry entry. It resolves duplicate codes according to registry precedence,
  rather than assuming an older duplicate remains the current lookup winner.
  Empty three-prime phosphate/cyclic ends have ambiguous source display strings
  and are checked-rejected; every record also roundtrips with flanking bases.
- Bracketed terminal records can appear in the middle of input, and later ones
  overwrite the corresponding end. Prefix/suffix lengths equal to sequence
  length fail. Zero-length slices can retain end records; a zero-length suffix
  following a sulfur-marked final residue receives the five-prime sulfur end.
- Empty sequences ignore end groups and charge when constructing their empty
  formula, but charged mass still subtracts charge times electron mass. The
  source's explicit empty N record contributes no residue atoms, while links
  still add `H-1PO2`. These computations do not invent a composition for N.
- The ten legacy fragment variants return the source backbone formula without
  charge hydrogens or terminal groups. Their mass still has the electron
  correction applied by the common mass accessor.
- Formula-derived sequence masses do not use a custom record's declared mono
  or average mass. Owned custom records remain usable after registry drop.
  Complete chemical identity distinguishes same-code formulas and declared
  masses, while value-equivalent copies compare and hash equally. A mismatched
  registry cannot silently serialize a sequence as different chemistry.
- TSV missing/`None` masses remain zero, while explicit zero with a nonempty
  formula triggers formula fallback. The new-code `N`/`GN` branch precedes
  deoxy/methyl base-loss heuristics; the deoxy branch precedes ambiguity. Source
  alternatives take the first and last space-delimited components. A final row
  without newline is retained.
- JSON retains explicit zero mono mass, unlike TSV. A four-element reference
  array selects the source wildcard branch based on length, even when its
  elements are not four base strings. A singleton base-specific `ApN` remains
  Anywhere. JSON `?*` ambiguity belongs to the provider entry; the record's
  `is_ambiguous()` only recognizes a final `?`. Unknown additional JSON fields
  are ignored by the source.

## Review scope and limits

The numerical reference tests complement the owners' direct provider,
configuration, allocation, mutation and invalid-input tests. They do not
substitute for those tests or constitute a runtime differential test against
C++. Full fields of live reader output are compared with the embedded data;
field-specific fixture checks are independent of both reader and generated
projection control flow. Formula fallback expected values reuse the existing
formula mass implementation and are therefore not independent validation of
the elemental mass table itself.

Native complete-value sequence ordering intentionally replaces source pointer
ordering and avoids the source comparison's early exit on equal code strings.
Custom registry context for later phosphorothioate slicing is owned explicitly.
These are documented native behaviors; no cross-process C++ pointer-order
parity is claimed. Resource limits, malformed input checks and checked integer
arithmetic similarly define native errors where the source could overrun,
overflow, or operate on undefined state.

The read-only implementation audit examined the three registry/provider modules
and NASequence against the pinned source. No actionable scientific discrepancy
remained in the inspected implementation. All eight reference tests pass in the complete 938-test runs on Rust 1.96 and
1.85, and in the no-default-feature checks on both compilers. The JSON-only
configuration also passes. Strict all-target Clippy, rustdoc, formatting and
registry regeneration checks pass. The final matrix is recorded in
[Validation](VALIDATION.md).

One numerical provenance limit deserves emphasis: C++ EmpiricalFormula stores
`std::map<const Element*, SignedSize>` and accumulates mass in pointer order.
Native formulas use deterministic element order. Consequently, exact equality
between the embedded fallback masses and live native provider output does not
establish bit-for-bit C++ formula-derived mass parity. The source-declared
mass literals retain independent exact binary64 checks. References and expected
values were changed only for a demonstrated source-semantic test assumption:
empty three-prime ends cannot roundtrip their standalone source display, so the
suite explicitly checks rejection and separately tests all records in context.
